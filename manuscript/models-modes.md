# 第07章 选择模型与模式：直接做、先讨论，还是先计划

你已经能把材料交给 WorkBuddy，也能让它生成文件。接下来，很容易遇到两个问题：界面里有不同模型，该选哪个？Ask、Plan、Agent 又有什么区别？

先从眼前的工作判断。你可能只是想弄懂一条通知，也可能希望先商量怎样同时修改几份材料，还可能已经把改动说得很清楚，只等它动手。这三种需求需要的工作方式不同，却不一定需要更换模型。

## 模型负责怎样理解，模式决定这次怎样做

*图：按需要的成果选工作方式：解释可以用Ask，复杂改动可先Plan，范围明确时用默认Agent推进。三种方式不必依次使用。*

第一章已经介绍过，模型承担理解、分析和生成。不同模型的处理能力和响应速度可能不同；同一份材料交给不同模型，结果也可能有差别。WorkBuddy 提供模型选择，也有与模型相关的能力设置。先用当前可用的默认模型完成本书练习；遇到具体困难，再判断是否需要更换。[官方模型说明](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Model)

任务模式回答的是另一个问题：这次要讨论、先列计划，还是执行？按照官方说明，Ask 用于问答和讨论；Plan 先形成计划，等你确认后再执行；默认的 Agent 用于实际推进任务，包括需要时处理文件。官方描述的模式选择位于输入区“+”菜单中，选择“模式”后可使用 Ask 或 Plan；未选择这两种时按默认 Agent 方式开展任务。选择后，先看输入区显示的当前模式，再发送请求。[官方输入区与模式说明](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Task-Bar)

这里最容易混淆的是 Ask 和 Plan：Ask 的成果可以就是一个解释；Plan 的成果是准备执行的步骤，需要你先判断步骤是否合适。例如，“这几份材料哪里冲突”适合先讨论；“按确认后的安排同时更新三份材料”则值得先审步骤。Agent 适合目标、材料和范围已经清楚的执行工作。

模式也不代替权限。它决定怎样推进这次工作，权限决定哪些动作能够执行。选了 Agent 仍可能需要授权；确认了 Plan，也不表示其中所有目录都已允许访问。下一章再把这两者放进文件整理练习。

## 同一批材料，可以从三个不同入口开始

继续使用[F02例会改期材料](../examples/F02/README.md)：现行说明确定了这一次例会的新安排，旧通知用于对照，较新的备忘仍是未批准建议。三种模式使用同一批材料，改变的是这次要求它做到哪一步。

下面三个请求是相互独立的用法，不是必须依次完成的流程。

第一种情况，你只想弄懂安排。选择 Ask，再提出问题。

**你**：请根据这三份材料，说明这次例会正式改了什么、什么没变。较新的备忘中哪些只是建议？先在对话里解释，不修改文件。

作者参考：回答应指出日期、时间、地点和交材料截止时间的变化，保留参加范围、提交方式不变，并说明远程接入与 16:00 开会尚未确认。此时，清楚的解释就是成果，没有必要额外生成文档。

第二种情况，你准备把正式安排用于通知、自己的日程摘要和材料提醒，担心漏掉一项。可以选择 Plan，先看这三项成果各需要做什么。本练习仍只用已有的三份输入，不需要寻找额外的日程文件。

**你**：请依据01-现行说明.txt，拟定修订02-旧通知.txt并生成一段日程摘要、一段材料提醒的步骤。先说明各项要采用哪些事实、保留哪些条件、还有什么真缺口。03-未确认备忘.txt不作为已确认安排。暂不修改或生成文件。

检查计划时，抓住三件会影响后续文件的事：依据是否正确、三个成果分别需要哪些变化、哪些条件必须保持。假如计划准备把“这一次改到周五”写成“以后每周五开会”，现在改正，只需改一处处理规则；等三份成果全做完，可能三份都要返工。先计划的价值就在这里。

发现计划把参加范围也改了，就指出：“参加范围保持原样，请删去这一项。”计划符合要求后，再使用该任务提供的执行入口或明确继续执行。只改一份短通知时，先计划可能比直接修改多一次往返，可以省去。

第三种情况，目标和依据已经清楚。使用默认 Agent，直接让它处理文件。

**你**：请读取练习文件夹中的02-旧通知.txt，以01-现行说明.txt为依据另写一份通知。只更新日期、时间、地点和交材料截止时间，参加范围与提交方式保持原样；未批准建议不要写入，并保留仅调整这一次的范围。另存为“例会通知_确认稿.txt”，保留原文件，完成后告诉我文件位置。

这次要检查真实文件是否存在、内容是否符合要求。它在聊天里解释得再好，也不能替代文件交付。

## 为什么换模型有时没有用

假设回答仍写着“周四开会”。先别急着换一个听起来更强的模型。回到任务检查：现行材料是否真的提供了？两份文件是不是同名，导致选错？请求是否只说了“整理通知”，没有说明需要以正式调整为准？

把原因查清后，可以这样续接：

**你**：你采用的是旧安排。请读取我刚补充的正式调整通知，以其中已确认内容修正日期、时间、地点和截止时间。备忘仍是建议，不作为正式安排。其他正确内容保留。

如果材料齐全、范围清楚，仍反复把“仅这一次”和“以后每次”混淆，再考虑调整当前可用的模型或相关能力设置。保留同一批输入和同一个要求，用这项已经知道答案的问题比较结果：能否准确区分适用范围，有没有新增错误，等待与检查是否值得。一次只改变一个重要条件，才容易判断改进来自哪里。

模型选择不是一次选出永远最强的型号。你需要的是这类任务中稳定可用的结果。某次写得更漂亮，也不能代替多份材料对照的准确性。

## 把选择变成一个很短的判断

发送前问自己一句：“我现在需要的是回答、处理方案，还是实际成果？”

需要理解问题，就先问；涉及多个文件和动作，先看一份计划可能更省返工；范围明确的小任务，直接做即可。讨论过程中也可能发现材料齐了，可以开始执行；执行时遇到新问题，也可以停下来补条件。工作方式跟着任务变化，不必给每项工作套上固定三步。

## 动手试一次

挑一个你已经做过的小任务，用一句话写清最终需要什么。若只是解释，不要求新建文件；若是交付文件，写清保存位置与原件处理。再给一个未选择的模式说明理由，例如“这次只改一处已确认时间，不需要单独做计划”。能这样判断，就已经够用。

## 卡住了，先检查什么

找不到与书中相同的模式入口时，先确认当前客户端是否提供该选项，再查看界面帮助。你仍可在请求里写清“先解释”“先给计划，等我确认”或“按以下范围直接处理”，并检查它有没有照做；文字要求有助于限定任务，但不能当成系统权限的替代。

采用错材料，先补依据；知道怎么改却无法写入，转到[权限章](permissions.md)；已经生成却找不到，转到[结果章](results.md)。模式只是定位问题的一项，不能代替这些条件。
